## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Тихонов Дмитрий Вячеславович |
| Вариант (запрос) | **Q18 — Large Volume Customer** |
| Масштаб `sfN` | **sf10** |
| Почему выбрал такой масштаб | SF1 (~6 млн строк в `lineitem`) выполняется за доли секунды, и различия между кодеками тонут в шуме прогрева и планировщика — на таком объёме бенчмарк не показывает ничего. SF100 (~107 млн строк `lineitem`, порядка 100 ГБ сырых данных) требует десятков гигабайт и часов на загрузку, что для одной практической избыточно. SF10 — точка, где разница в размере и скорости сжатия становится устойчивой, а весь стек вместе с Trino работает |

## 2. Поднятые сервисы — и почему именно они

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Даёт тот же протокол, что AWS S3, но локально: код загрузки и Trino-коннектор не меняются при переезде в облако. Локальная ФС не подходит — Iceberg нужен объектный слой с атомарной записью и версионированием |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Lakekeeper хранит состояние каталога в реляционной БД. Postgres — штатная опция, даёт транзакционность операций с каталогом: конкурентные коммиты сериализуются, а не бьются за файлы |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Реализует стандартный Iceberg REST API, поэтому Trino, Spark или DuckDB подключаются к нему одинаково — каталог не привязан к движку. В отличие от Hadoop-каталога, состояние в БД, а не в файлах: нет лишних листингов S3 и проблем с согласованностью |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Разделяет compute и storage: ничего не хранит сам. Умеет писать в Iceberg через CTAS и понимает parquet/orc/avro напрямую — без этого бенчмарк форматов не сделать. Альтернатива Spark тяжелее в развёртывании |
| Metabase | отчёт/дашборд поверх Gold | Поднимается одним контейнером без внешней БД, есть готовый Trino-драйвер, даёт self-service-дашборды без написания SQL. |

### Скрипты, которыми поднимал стек

```bash
# 1. Поднять все сервисы (MinIO, Postgres, Lakekeeper, Trino, Metabase)
cd lakehouse

# 2. Дождаться готовности Trino
until curl -sf http://localhost:8080/v1/info >/dev/null; do sleep 3; done

# 3. Bootstrap Lakekeeper: принять условия, создать каталог и warehouse в MinIO
bash scripts/02-lakekeeper-bootstrap.sh

# 4. Залить Bronze (сырые customer/orders/lineitem из tpch.sf10)

# 5. Silver: агрегация, фильтр, нормализация, обогащение
docker exec -i lakehouse-trino trino --file /dev/stdin < sql/02_silver.sql

# 6. Gold: витрина
docker exec -i lakehouse-trino trino --file /dev/stdin < sql/03_gold.sql

# 7. Замеры для §5
docker exec -i lakehouse-trino trino --file /dev/stdin < sql/04_benchmark.sql

# 8. Размер таблиц в MinIO
docker exec lakehouse-mc mc du local/warehouse/bronze/
docker exec lakehouse-mc mc du local/warehouse/silver/
docker exec lakehouse-mc mc du local/warehouse/gold/


```

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `customer` | `c_custkey`, `c_name`, `c_mktsegment`, `c_nationkey` | джойн с `orders` по ключу клиента; вывод имени; обогащение сегментом рынка |
| `orders` | `o_orderkey`, `o_custkey`, `o_orderdate`, `o_totalprice`, `o_orderpriority` | джойн с `customer` и `lineitem`, фильтр по `o_orderkey`, вывод даты и суммы, сортировка |
| `lineitem` | `l_orderkey`, `l_quantity`, `l_extendedprice` | агрегат `sum(l_quantity)`, `HAVING > 300` в подзапросе, джойн по `o_orderkey` |

## 4. Медальон — решения по каждому слою

### Bronze (сырой)

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `bronze.customer` | все 8 (`c_custkey` … `c_comment`) | 1500000 | 77.4 | PARQUET | ZSTD | нет | Ничего не отбрасываю: сырой слой должен повторять источник, иначе потеряется возможность пересобрать Silver под новые требования. Parquet — колоночный, читает только нужные колонки (Q18 трогает 2 из 8 здесь и 2 из 16 в lineitem). ZSTD — сжатие уровня GZIP при записи в 6 раз быстрее. Партиций нет: сырьё перезаписывается целиком, партиции только мешают |
| `bronze.orders` | все 9 (`o_orderkey` … `o_comment`) | 15000000 | 348.4 | PARQUET | ZSTD | нет | то же |
| `bronze.lineitem` | все 16 (`l_orderkey` … `l_comment`) | 59986052 | 1424.2 | PARQUET | ZSTD | нет | то же; самая большая таблица, здесь выбор кодека влияет сильнее всего |

### Silver (очищенный)

| Таблица | Колонки (что оставил) | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `silver.lineitem_by_order` | `orderkey`, `total_quantity`, `line_count`, `extended_price` | 15000000 | 125.1 | PARQUET | ZSTD | нет | Предварительная агрегация: в исходном запросе `sum(quantity)` считается дважды — в `HAVING` и во внешнем `GROUP BY`. Здесь агрегат считается один раз. 16 колонок сворачиваются в 4 — таблица меньше исходной в разы |
| `silver.large_orders` | `orderkey`, `total_quantity`, `line_count`, `extended_price` | 570| 0.05 | PARQUET | ZSTD | нет | Селективный фильтр `total_quantity > 300` до джойнов: отсекает 99.996% заказов. |
| `silver.order_enriched` | `custkey`, `customer_name`, `mktsegment`, `nationkey`, `orderkey`, `orderdate`, `totalprice`, `orderpriority`, `total_quantity`, `line_count`, `extended_price`, `avg_unit_price` | 570 | 0.08 | PARQUET | ZSTD | нет | Нормализация (снятие префиксов `c_`/`o_`/`l_`, типизация `DATE`, `DECIMAL`) + обогащение полями `mktsegment`, `orderpriority` и производным `avg_unit_price`. Готовая плоская таблица под аналитику, без джойнов на лету |

### Gold (витрина)

| Таблица | Колонки | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---|---|---|---|---|---|
| `gold.q18_top100` | `customer_name`, `custkey`, `orderkey`, `orderdate`, `totalprice`, `total_quantity`, `mktsegment`, `orderpriority`, `rnk` | 100 | <<1 | PARQUET | ZSTD | нет | Денормализованная витрина с готовым ранжированием — BI-инструмент не должен считать rank() сам. На SF10 крупных заказов 570, то есть LIMIT 100 срабатывает и витрина содержит ровно 100 строк. Гранулярность строки = заказ (GROUP BY включает orderkey, как в исходном запросе), поэтому один клиент может занимать несколько строк топа — это зафиксированное решение, а не недосмотр. Партиционирование на 100 строках не имеет смысла |

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Мой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная БД дорого масштабируется по объёму (хранилище и вычисление в одном узле) и плохо терпит разнородные сырые данные, ещё не приведённые к схеме. Обычное файловое хранилище дёшево и безгранично, но не даёт схемы, транзакций и SQL — файлы легко «потерять» при параллельной записи. Lakehouse берёт обе стороны: данные лежат открытыми файлами в дешёвом объектном хранилище (нет вендор-лока), а каталог метаданных поверх них (Iceberg) добавляет ACID-транзакции, схему, снапшоты и time travel. Вычисление отделяется от хранения, поэтому движок (Trino, Spark) можно менять или масштабировать независимо от данных. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | `ALTER TABLE iceberg.silver.order_enriched ADD COLUMN region varchar;` — операция **только с метаданными**: старые parquet-файлы не перезаписываются, для них новая колонка читается как `NULL`. Схема меняется мгновенно даже на терабайтах. Переименование `ALTER TABLE ... RENAME COLUMN mktsegment TO market_segment;` тоже не двигает данные — меняется только маппинг `field_id → имя` в метаданных Iceberg (колонки идентифицируются по id, а не по позиции или имени). Практическая ценность: Silver расширяется под новые требования BI без перезаписи истории. |
| Пример скрипта восстановления данных из снапшота (time travel) | см. ниже |

```sql
-- 1. Список снапшотов таблицы
SELECT snapshot_id, committed_at, operation
FROM iceberg.silver."order_enriched$snapshots"
ORDER BY committed_at DESC;

-- 2. Прочитать состояние на момент ДО ошибочной перезаписи
SELECT count(*)
FROM iceberg.silver.order_enriched
FOR VERSION AS OF 1234567890123456789;

-- 3. Сравнить с текущим состоянием
SELECT count(*) FROM iceberg.silver.order_enriched;

-- 4. Откатить таблицу к этому снапшоту
ALTER TABLE iceberg.silver.order_enriched
EXECUTE rollback_to_snapshot(1234567890123456789);
```


### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| **Metabase** (BI) | Поднимается одним контейнером без внешней БД (хранит состояние в H2), имеет готовый драйвер Trino, даёт self-service-дашборды без написания SQL. Superset мощнее в кастомизации, но требует Redis и Celery-воркеров. Показывает именно то, что нужно по заданию: взаимодействие с данными **Bronze**-слоя через UI. |

**Скрипт развертывания** (в составе общего compose):

```bash
docker compose up -d metabase
# Metabase: http://localhost:3000
```

**Мои действия в UI — как подключился и увидел Bronze:**

1. Открыл http://localhost:3000, прошёл первичную настройку.
2. **Add database** → тип **Trino**, host `trino`, port `8080`, catalog `iceberg`, schema `bronze`, пользователь любой (аутентификация в локальном Trino отключена).
3. **Browse data** → `iceberg` → `bronze` → таблицы `customer`, `orders`, `lineitem` видны в списке.
4. Открыл `lineitem` → **Native query** → выполнил проверку:

```sql
SELECT count(*) FROM iceberg.bronze.lineitem;      
SELECT count(*) FROM iceberg.silver.large_orders;  
SELECT count(*) FROM iceberg.gold.q18_top100;      
```

5. Собрал дашборд «Q18 — крупные заказы» на `gold.q18_top100`:

```sql
-- выручка по сегментам рынка
SELECT mktsegment, count(*) AS orders, round(sum(totalprice), 2) AS revenue
FROM iceberg.gold.q18_top100 GROUP BY 1 ORDER BY revenue DESC;

-- топ-10 клиентов
SELECT customer_name, orderdate, totalprice, total_quantity
FROM iceberg.gold.q18_top100 ORDER BY rnk LIMIT 10;
```

## 7. Выводы

В работе развёрнут локальный lakehouse (MinIO + Lakekeeper + Trino + Metabase) и реализован медальон под TPC-H Q18: Bronze хранит сырые `customer`/`orders`/`lineitem` в parquet/ZSTD, Silver выполняет предварительную агрегацию `lineitem` до гранулярности заказа с фильтром `sum(quantity) > 300`, Gold — витрина из 57 заказов; корректность подтверждена построчным совпадением с исходным запросом из задания.

Главное архитектурное решение — перенос агрегации в Silver: исходный запрос считает `sum(quantity)` дважды (в `HAVING` и во внешнем `GROUP BY`), медальон делает это один раз и фильтрует до джойнов, что эквивалентно по результату, но устраняет двойной пересчёт.

Сравнение кодеков показало, что ZSTD даёт сжатие уровня GZIP (разница 0.6%) при записи в 6.4 раза быстрее, поэтому выбран он; SNAPPY отвергнут из-за файлов на 42% больше. По скорости чтения разрыв между кодеками в пределах шума — на таких объёмах выигрыш даёт колоночное хранение и предварительная агрегация, а не сам кодек.

По сравнению с обычной БД lakehouse даёт независимое масштабирование хранения и вычисления плюс ACID и time travel поверх дешёвых открытых файлов; по сравнению с файловым хранилищем — схему, транзакции и SQL.
